# Spec: Resolv build (T4–T27, unattended)

## Problem
Team Xeon has one day to turn the Resolv design (docs 01, 02, 06) into a working prototype for the Paytm Build for India finals. Phase 1 (T1–T3: scaffold, mock Paytm, domain/DB/audit) is built attended. The remaining work, T4 to T27, is the agent loop, the policy gate, the cockpit, incidents, evals and polish. That is too much for the humans to type and still rehearse, so an unattended factory-conductor run builds it. Each task has to be proven by a machine with no network, no running server and nobody watching.

## Users
- Judges: in about 60 seconds, they see what Resolv does on its own, what is gated, and why it is safe (demo moments D1–D5).
- Support agent "Priya" (demo persona): works a queue of only the tickets that need judgement, and approves or overrides with one click.
- Ops lead (demo persona): sees incidents, SLA risk, notifications and KPIs.
- Team Xeon developers: start the unattended run after phase 1, review the run branch, then warm the cache and rehearse by hand.

## Goals
- From the cockpit in replay mode, with no network calls to Paytm, judges see D1 (₹2,499 reversal plus ₹200 compensation, RESOLVED), D2 (one AXIS incident absorbing 120 tickets), D3 (₹12,000 reversal approved by a named human), D4 (an audited override) and D5 (an eval report with n ≥ 58).
- Every acceptance check of this run passes in an isolated clone with `LLM_MODE=mock`, no running server and no calls to Anthropic or Paytm.
- The policy gate, idempotency and audit trail hold on every path, including human approvals and overrides.

## Non-goals
- T28 Postgres (docker compose, psycopg, pgvector): SQLite only.
- T29 Freshdesk helpdesk adapter.
- T25 live cache warm-up: running `scripts/warm_cache.sh` with `LLM_MODE=live` and committing `backend/.llm_cache/` needs network and an API key. It is attended work after the run.
- T26 rehearsal x3, the backup video and the deck update: these are human work.
- The T27 git tag `v0.1-finals` and the Q&A sheet: a human tags after reviewing the run branch.
- Playwright or other E2E `*.ts` specs (D7).

## Constraints
- B1 [goal]: Maximise what judges see working: D1–D5 run end to end from the cockpit in `LLM_MODE=replay`, with the canonical facts in CLAUDE.md (D1 ₹2,499 reversal plus ₹200 compensation, D3 ₹12,000 to NEEDS_APPROVAL, D2 AXIS/UPI_SWITCH_DOWN threshold 10 in 60 min).
- B2 [boundary]: One-day build. The run implements only T4–T27 of docs/06 in 06 order, minus the non-goals. Nothing beyond 06's file lists.
- T1 [invariant]: The LLM never moves money. Model output is a `Decision`; every proposed action passes `app/policy/engine.py` and executes only through `ToolRegistry.call()` after `AUTO_EXECUTE` or a human approval (CLAUDE.md hard rule 1).
- T2 [invariant]: Enums, ids, table and column names, routes, file paths, env vars and action names are exactly as in docs/02. New fields are marked `(decision: …)` (hard rule 3).
- T3 [invariant]: Every action execution computes `sha256(ticket_id + name + canonical params)` and checks `action_executions` first; a retry never double-refunds (hard rule 5).
- T4 [invariant]: LLM calls use `temperature=0`, structured output via tool-use and `max_tokens` ≤ 1500. Prompts live in `app/agent/prompts/*.md` (hard rule 8).
- T5 [invariant]: `LLM_MODE=mock` with the mounted mock Paytm runs the 7 scenarios with no network, and no test depends on the Anthropic API (hard rule 11).
- T6 [boundary]: SQLite via `create_all`/`reset` only. No migrations, no Postgres, no Celery or external queue, no services beyond the docs/02 §2 layout.
- T7 [invariant]: Demo inputs are deterministic (fixed scenario ids, seeded `random.Random` for spike and eval data), so replay-cache keys match on stage (pre-mortem: users).
- T8 [boundary]: During a 120-ticket spike, incident-matched tickets make 0 LLM calls and `/api/health` answers in < 300 ms (pre-mortem: system).
- T9 [invariant]: The agent loop is the docs/02 §3 LangGraph `StateGraph` in `agent/graph.py`, and `AGENT_ENGINE=langgraph|runner` selects it or the sequential `agent/runner.py` fallback over the same pure nodes and §3.2 edges; both engines run the 7 scenarios in mock mode (D5, D9).
- S1 [invariant]: No call to a real Paytm endpoint. `PAYTM_BASE_URL` points at `/mock/paytm/v1` or the standalone mock on `:8001`; any other value is refused (hard rule 2).
- S2 [invariant]: PII is masked by `app/policy/pii.py` before any LLM call. The UI shows `masked_text` by default, and raw phone, email, VPA or account numbers are never logged (hard rule 6).
- S3 [invariant]: No `eval()` or `exec()` anywhere, including the rules expression evaluator (hard rule 7).
- S4 [invariant]: The gate resolves `txn/refund/settlement/kyc/mandate` ids only from the `ContextBundle`; anything else is `BLOCKED unknown_reference` (hard rule 9).
- O1 [invariant]: Every tool call writes `tool_call` and `tool_result`, every node writes its docs/02 §3.2 audit kind, and approvals, overrides, notifications and incident links are audited with `actor` (hard rule 4).
- O2 [invariant]: Each task stays inside its file list. No refactors, renames, dependency swaps or "while I'm here" changes (hard rule 10, D1).
- O3 [invariant]: Every acceptance check runs in-process from the repo root of an isolated clone, with no running server, no shell and no calls to Anthropic or Paytm (package installs by `uv` and `npm ci` are allowed). It names its test file (never `-k`), and tests pin `LLM_MODE=mock` themselves (pre-mortem: build/run).
- U1 [boundary]: The cockpit is projected. Large badges and numbers readable at 3 m, Tailwind only, palette navy #002E6E, cyan #00BAF2, light #F2F6FB, text #0B1F3A (D4).
- U2 [boundary]: Every cockpit page polls with `useSWR` `refreshInterval: 2000`, so a backend state change shows within 2 s.

## Pre-mortem
- Users: on stage the replay cache missed because spike texts or ids differed from the warm-up run, the live call stalled, and judges watched a frozen queue. Prevention: T7 (deterministic inputs) and U2 (2 s polling).
- System: a 120-ticket spike sent 120 tickets through understand and decide, the queue stalled and `/api/health` timed out mid-demo. Prevention: T8 (incident-matched tickets skip the LLM, health < 300 ms).
- Build/run: the unattended run merged tasks whose proof was a `pytest -k` filter that matched nothing, or a test that silently called Anthropic through `.env.example`'s `LLM_MODE=replay`. Main looked green but D1 failed offline. Prevention: O3 (named test files, in-process, mock pinned in `conftest.py`).

## Tensions
- TN1 [resource_tension]: Docs/02 wires a LangGraph `StateGraph` plus a runner fallback, and two engines cost time in a one-day build (between: T9, B2, T2; status: resolved; strategy: Partition; decision: D9)
- TN2 [trade_off]: Fixed auto limits (₹5,000 refund, ₹1,000 compensation) and human-only categories lower the auto-resolution rate judges see (between: T1, S4, B1; status: resolved; strategy: Prioritize)
- TN3 [trade_off]: PII masking can hide entities the LLM needs to pick the right transaction (between: S2, B1; status: resolved; strategy: Transform)
- TN4 [hidden_dependency]: Replay determinism depends on byte-identical prompts, while live LLM output and an empty cache in a fresh clone break offline checks (between: T5, T7, O3; status: resolved; strategy: Partition; decision: D6)
- TN5 [trade_off]: Offline machine checks cannot see a projected page, but the cockpit is half the demo (between: O3, U1, U2; status: accepted; strategy: Accept; decision: D7)

## Tension resolutions
- TN1: Partition the engine from the logic. All behaviour lives in the pure node functions and one shared edge function; `graph.py` and `runner.py` are thin wirings of it, and one parametrised test runs the 7 scenarios on both (D9). This tightens O2 and violates nothing.
- TN2: Safety wins. Limits stay as in `rules.yaml`, and the eval report shows the trade-off (gate catch rate next to auto-resolution rate).
- TN3: Mask only the PII classes (phone, email, VPA, account, card, Aadhaar, PAN). Ledger ids such as `txn_…` stay unmasked, so the LLM can still reference them and S4 still blocks unknown ids.
- TN4: Tests and checks use `mock` only (D6). A replay miss with no API key falls back to `mock` and logs `cache_miss` (D10). Live warm-up is attended (Non-goals).
- TN5: Frontend proof is `next build` plus the verify skill driving the page (D7).

## Solution options
- OPT-A: LangGraph `StateGraph` in `agent/graph.py` plus the `agent/runner.py` fallback, selected by `AGENT_ENGINE`, as docs/02 §3 describes (complexity: Medium; reversibility: TWO_WAY; satisfies: RT1, RT2, RT3, RT4, RT5, RT6, RT7, RT8, RT9, RT10)
- OPT-B: Runner only. `agent/runner.py` runs the same pure nodes with the §3.2 edge logic, and there is no `graph.py` and no `langgraph` import (complexity: Low; reversibility: TWO_WAY; satisfies: RT1, RT2, RT3, RT4, RT5, RT6, RT7, RT8, RT9)
- OPT-C: LangGraph only, with no runner fallback (complexity: Medium; reversibility: REVERSIBLE_WITH_COST; satisfies: RT1, RT2, RT3, RT5, RT6, RT7, RT8)

Recommended: OPT-A — it is the only option that satisfies RT10 (the docs/02 §3 graph with a runner fallback, both passing the scenarios), and the shared pure nodes keep `AGENT_ENGINE=runner` a one-line switch on stage (decision: D9)
